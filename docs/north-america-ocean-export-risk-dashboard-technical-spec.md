## 2. 목적

본 문서는 북미향 해상 수출 과정에서 발생하는 일정, 운임, 항만, 통관, 서류, 규제 및 외부 이벤트 위험을 통합 관리하는 대시보드의 기술 설계를 정의한다.

시스템은 다음 결과를 제공해야 한다.

1. 고위험 선적을 조기에 식별한다.
2. 위험의 원인, 근거 데이터, 예상 영향을 설명한다.
3. 담당자, 대응기한, 권고 조치 및 승인자를 연결한다.
4. 지연과 추가 비용의 발생 및 회피 효과를 측정한다.
5. 대시보드 수치에서 원본 데이터와 계산식까지 역추적할 수 있게 한다.

## 3. 범위

### 3.1 포함 범위

- 선적·Booking·B/L·컨테이너 정보 수집
- ETD, ATD, ETA, ATA 및 변경 이력 관리
- 선적 전 서류와 Cut-off 상태 점검
- 미국 ISF 및 캐나다 ACI 관련 상태 관리
- 항만 혼잡, 기상, 파업, Blank Sailing 등 외부 위험 반영
- HS 코드, 원산지, 통관 보류 및 검사 상태 관리
- Demurrage, Detention, Storage 비용 노출 계산
- 선적별 위험점수 및 위험등급 계산
- 경보 생성, 배정, 승인, 조치, 종료 이력 관리
- KPI 집계 및 월간 측정 로그 생성
- 오프라인 단일 HTML 임원 대시보드 생성

### 3.2 제외 범위

- 선사 시스템에서 Booking을 자동 변경하는 기능
- 세관 신고를 무인으로 제출하는 기능
- 담당자 승인 없이 고객에게 메시지를 발송하는 기능
- 결제, 보험금 청구 및 보상처리 자동 실행
- 실시간 AIS 구독 서비스의 직접 구축
- 운영 초기 단계의 머신러닝 자동 재학습

## 4. 전제 및 미확정 사항

### 4.1 설계 전제

- MVP는 CSV 또는 JSON 배치 입력을 지원한다.
- 일별 1회 이상 갱신을 기본으로 한다.
- 대시보드는 인터넷 없이 실행되는 단일 HTML 파일로 배포할 수 있다.
- 예측값과 실적값은 저장 단계부터 분리한다.
- 누락값은 `0`으로 변환하지 않고 `미수집`, `해당 없음`, `산출 대기` 중 하나로 관리한다.
- 시스템 시간 저장 기준은 UTC이며, 화면에는 업무 기준 현지시간을 함께 표시한다.

### 4.2 미확정 사항

| 항목 | 상태 | 확정 방법 |
|---|---|---|
| 데이터 원천 시스템 | 산출 대기 | 운영 부서 인터뷰 및 파일 조사 |
| 일평균 선적 건수 | 산출 대기 | 최근 12개월 실적 분석 |
| 위험점수 임계값 | 가정값 | 과거 사고·지연 데이터로 검증 |
| KPI 목표값 | 산출 대기 | 최근 6~12개월 기준선 산출 |
| 비용 승인 한도 | 산출 대기 | 결재 규정 확인 |
| 데이터 보존기간 | 산출 대기 | 법무·보안 정책 확인 |
| 외부 위험 데이터 API | 산출 대기 | 정확도·비용·라이선스 평가 |

### 6.2 기준 구현 방식

MVP의 기준 구현은 재현성과 오프라인 배포를 우선한다.

| 계층 | 기준 구현 | 선택 이유 |
|---|---|---|
| 수집·변환 | Python 기반 배치 작업 | CSV·JSON 처리와 규칙 테스트 용이 |
| 운영 저장 | SQLite 또는 동등한 관계형 저장소 | 로컬 실행, 트랜잭션, 감사 이력 지원 |
| 규칙 관리 | 버전이 부여된 설정 파일과 평가 모듈 | 임계값 변경 추적 및 테스트 가능 |
| KPI 계산 | 재실행 가능한 집계 작업 | 월별 결과와 산식 버전 재현 |
| 화면 | 인라인 CSS·JavaScript를 포함한 단일 HTML | 네트워크 없이 배포 가능 |
| 차트 | 인라인 SVG 또는 Canvas | 외부 CDN 의존 제거 |
| 시험 | 자동 단위·통합 테스트와 브라우저 검수 | 계산과 화면을 함께 검증 |

특정 제품이나 라이브러리는 구현 착수 시 조직 표준, 라이선스, 지원 브라우저 및 운영환경을 검토해 확정한다. 기술을 변경해도 데이터 계약, 위험 규칙, KPI 산식, 추적성 및 수용 기준은 동일하게 유지한다.

### 6.3 배포 단위

- `input/`: 승인된 원본 입력
- `staging/`: 검증 및 표준화 중간 데이터
- `data/`: 운영 데이터베이스 또는 정규화 결과
- `config/`: 규칙, 코드, KPI 및 승인 기준
- `logs/`: 처리·품질·감사 로그
- `outputs/day5-dashboard-prd/`: PRD, KPI, 측정 로그 및 최종 대시보드

운영 배포물에는 자격증명, API 키, 원본 개인정보 또는 개발자 로컬 절대경로를 포함하지 않는다.

## 7. 데이터 처리 파이프라인

### 7.1 처리 순서

1. 입력 파일 또는 API 응답을 원본 상태로 저장한다.
2. 파일명, 해시, 수집시각, 기준일, 출처를 기록한다.
3. 스키마와 필수값을 검증한다.
4. 중복 레코드를 식별한다.
5. 날짜, 시간대, 통화, 코드 값을 표준화한다.
6. 선적·컨테이너·이벤트·문서·비용 데이터를 연결한다.
7. 데이터 품질점수와 필드별 신뢰도를 계산한다.
8. 위험 규칙을 실행한다.
9. 경보를 생성하거나 기존 경보를 갱신한다.
10. KPI와 비용 노출을 집계한다.
11. 추적성 정보와 함께 대시보드 데이터를 생성한다.

### 7.2 멱등성과 중복 처리

- `source_system + source_record_id + updated_at`을 기본 멱등 키로 사용한다.
- 원천 식별자가 없으면 파일 해시와 행 번호를 보조키로 사용한다.
- 같은 이벤트를 재수집해도 중복 경보를 만들지 않는다.
- 위험 원인과 대상이 같고 기존 경보가 열린 상태면 동일 경보를 갱신한다.
- 위험이 해소돼도 기록을 삭제하지 않고 종료 상태로 보존한다.

### 7.3 오류 처리

| 오류 유형 | 처리 |
|---|---|
| 필수 키 누락 | 격리 영역 이동, 운영 집계 제외 |
| 날짜 파싱 실패 | 원문 보존, `미수집` 처리, 오류 로그 |
| 알 수 없는 코드 | 원문 보존, 매핑 대기 큐 등록 |
| 중복 입력 | 최신 수정시각 기준 병합, 충돌 기록 |
| 환율 부재 | 원통화 유지, 환산액 `산출 대기` |
| 외부 데이터 실패 | 직전 성공값의 기준시각 표시, 신선도 경고 |

## 10. 위험 규칙 및 점수 엔진

### 10.1 점수 산식

초기 규칙 기반 점수는 다음 산식을 사용한다.

```text
raw_score = probability_score × impact_score × urgency_score
normalized_score = raw_score ÷ 125 × 100
total_score = normalized_score × (0.7 + 0.3 × confidence)
```

- `probability_score`: 0~5
- `impact_score`: 0~5
- `urgency_score`: 0~5
- `confidence`: 0~1
- 최종 점수: 0~100

데이터 신뢰도가 낮을 때 위험을 제거하지 않고 점수를 보수적으로 보정하며, 별도의 데이터 품질 경보를 표시한다.

### 10.2 초기 등급

| 점수 | 등급 | 대응 |
|---:|---|---|
| 0~29 | NORMAL | 정기 모니터링 |
| 30~59 | WATCH | 담당자 확인 |
| 60~79 | HIGH | 조치와 기한 등록 |
| 80~100 | CRITICAL | 즉시 조치 및 관리자 보고 |

위 임계값은 가정값이며 과거 데이터 검증 후 변경한다. 변경 시 버전과 적용일을 감사 로그에 기록한다.

### 10.3 초기 위험 규칙

| 규칙 ID | 조건 예시 | 기본 대응 |
|---|---|---|
| SCH-001 | 현재 ETA가 최초 ETA보다 허용일 이상 지연 | 고객 납기 영향 확인 |
| SCH-002 | ETD 임박 상태에서 Booking 미확정 | 선사 확인 또는 대체 항차 검토 |
| SCH-003 | 환적 예정시간이 최소 연결시간 미만 | 환적 실패 가능성 확인 |
| DOC-001 | Cut-off 임박 및 필수서류 미완료 | 서류 담당자 즉시 배정 |
| DOC-002 | B/L, CI, PL 간 중량·수량 불일치 | 원본 검증 및 정정 |
| CUS-001 | ISF 또는 ACI 기한 임박 및 미제출 | 신고 담당자 긴급 알림 |
| CUS-002 | 통관상태 HOLD 또는 EXAM | 보류 사유와 추가자료 확인 |
| CST-001 | Free Time 잔여일이 경고 기준 이하 | 반출계획 및 비용 승인 검토 |
| CST-002 | 예상 추가비용이 승인 한도 초과 | 관리자 승인 요청 |
| EXT-001 | 출발·도착·환적항에 파업 또는 폐쇄 이벤트 | 대체 항만·항차 검토 |
| EXT-002 | 항로상 중대 기상 이벤트 발생 | ETA 재평가 및 고객 통지 검토 |
| DQ-001 | 필수 위치·일정 데이터가 신선도 기준 초과 | 데이터 원천 확인 |

각 규칙에는 버전, 적용일, 소유자, 근거, 임계값, 예외조건, 테스트 사례를 부여한다.

### 10.4 경보 억제 및 병합

- 같은 선적, 같은 규칙, 같은 원인으로 열린 경보는 병합한다.
- 경보 점수가 상위 등급으로 이동하면 재알림한다.
- 수동 억제는 사유와 종료시각을 필수로 기록한다.
- 종료된 경보가 동일 원인으로 다시 발생하면 재발 경보로 연결한다.
- 데이터 결측만으로 정상 판정하지 않는다.

## 11. 업무 워크플로

```text
NEW → ACKNOWLEDGED → PENDING_APPROVAL → IN_PROGRESS → RESOLVED
                    ↘ REJECTED
RESOLVED → REOPENED
```

### 11.1 상태 전이 규칙

| 현재 상태 | 다음 상태 | 필수 조건 |
|---|---|---|
| NEW | ACKNOWLEDGED | 담당자 및 확인시각 |
| ACKNOWLEDGED | PENDING_APPROVAL | 조치안, 비용, 승인자 |
| ACKNOWLEDGED | IN_PROGRESS | 승인이 필요 없는 조치 |
| PENDING_APPROVAL | IN_PROGRESS | 승인 완료 |
| PENDING_APPROVAL | REJECTED | 반려 사유 |
| IN_PROGRESS | RESOLVED | 결과, 완료시각, 증빙 |
| RESOLVED | REOPENED | 재발 사유 |

중대 위험, 규제 위험 및 비용 한도 초과 건은 승인 없이 실행 완료 처리할 수 없다.

## 13. ROI 계산

```text
총편익 = 회피한 지연 페널티
       + 회피한 긴급운송비
       + 감소한 Demurrage·Detention·Storage
       + 감소한 벌금·통관 오류 비용
       + 절감한 운영시간의 환산가치

ROI(%) = (총편익 - 총비용) ÷ 총비용 × 100
```

### 13.1 계산 원칙

- 보수, 기준, 낙관 3개 시나리오를 제공한다.
- 일회성 구축비와 반복 운영비를 분리한다.
- 추정값과 실측값을 분리한다.
- 측정 기간과 할인율 적용 여부를 명시한다.
- 비용 회피의 기준 시나리오와 증빙을 저장한다.
- 실데이터가 없는 경우 결과를 `산출 대기`로 표시한다.

## 21. 수용 기준

### 21.1 기능 수용 기준

- 사용자는 고위험 선적을 30초 이내 찾을 수 있다.
- 사용자는 2회 이내의 상호작용으로 위험 근거를 확인할 수 있다.
- 각 열린 경보에는 담당자와 대응기한이 존재한다.
- 승인 필요 건을 별도 목록에서 확인할 수 있다.
- 예측값과 실적값이 명확히 구분된다.
- 계산 불가능한 값은 `산출 대기`로 표시된다.

### 21.2 데이터 수용 기준

- KPI 이름, 값, 단위, 기준일, 원본 파일을 추적할 수 있다.
- 누락값을 0으로 치환하지 않는다.
- 합계와 평균을 혼동하지 않는다.
- 데이터 기준시각과 생성시각을 표시한다.
- 표본 대조 대상 수치가 모두 허용오차 내에 있다.

### 21.3 화면 수용 기준

- KPI 카드 4개 이상, 차트 2개 이상, 주요 위험 3건 이상을 표시한다.
- 다음 행동에 담당자와 기한이 포함된다.
- 1366×768과 390×844에서 내용이 잘리거나 겹치지 않는다.
- 브라우저 콘솔 오류가 없다.
- 외부 URL, CDN, 외부 폰트, 외부 이미지, 로컬 절대경로가 0건이다.
- 인터넷 연결 없이 단일 HTML이 정상 실행된다.
- 임원 보고가 현황, 위험, 기회, 의사결정 요청 순으로 5분 이내 가능하다.

## 24. 변경관리

- 데이터 계약, 위험 규칙, KPI 산식은 독립적으로 버전 관리한다.
- 변경 요청에는 목적, 영향 범위, 이전·이후 정의, 적용일, 승인자를 기록한다.
- 과거 KPI는 당시 적용한 산식 버전을 유지한다.
- 임계값 변경 전후의 경보량과 오탐·미탐 영향을 비교한다.
- 운영 중 발견된 예외는 즉시 코드에 하드코딩하지 않고 규칙 변경 절차를 거친다.

## 25. 릴리스 게이트

### Gate 1: 데이터 준비

- 필수 데이터 원천과 소유자가 승인됐다.
- 스키마, 코드, 단위 및 기준시각 규칙이 확정됐다.
- 격리되는 오류 데이터와 운영 집계 대상의 경계가 검증됐다.

### Gate 2: 위험·KPI 계산

- 위험 규칙별 정상, 경계, 오류 사례 테스트가 통과했다.
- KPI 분자·분모와 제외조건이 업무 담당자에게 승인됐다.
- 최소 5개 수치의 원본 표본 대조가 통과했다.

### Gate 3: 워크플로·보안

- 담당자 배정, 승인, 반려, 완료 및 재오픈 흐름이 검증됐다.
- 역할별 권한과 민감정보 노출 여부가 검토됐다.
- 변경·승인·보정 이력이 감사 로그에 남는다.

### Gate 4: 대시보드

- KPI 카드, 차트, 위험 및 다음 행동의 최소 구성을 충족한다.
- 데스크톱과 모바일 기준 화면에서 깨짐이 없다.
- 콘솔 오류와 외부 네트워크 의존성이 없다.
- 모든 표시 수치에서 원본과 계산 근거를 확인할 수 있다.

### Gate 5: 운영 전환

- 배치 실패, 데이터 지연 및 복구 절차가 리허설됐다.
- KPI 목표, 위험 임계값, 승인 한도와 운영 책임자가 확정됐다.
- 임원용 5분 보고 시나리오와 사용자 교육이 완료됐다.
